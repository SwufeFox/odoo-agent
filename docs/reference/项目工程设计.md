# 显微镜企业智能办公系统顶层架构与 MVP 工程设计报告

## 一、项目破局策略与不确定性收敛框架

针对初创期显微镜设备企业的数字化建设诉求，当前工程设计的核心矛盾在于客户需求尚处于高模糊度的意向阶段，而软件工程交付要求具备严密的边界定义、可量化的工作量估算以及无歧义的验收标准。显微镜设备行业涵盖光学部件、精密机械载物台、光电探测器及配套控制系统的组装与贸易，具有典型的多品种、小批量、高单价零部件采购特征，供应商询报价往来频繁，且零部件技术规格书与质保合同高度绑定。若在未明确业务流转细节与组织架构的前提下直接进入编码阶段，实施团队极易陷入无限期的需求蔓延与免费运维泥潭。

为实现从模糊意向到可报价工程项目的转化，顶层设计必须确立两项核心架构纪律。第一项纪律是明确 Odoo ERP 为唯一业务事实来源（Single Source of Truth），而 AI Agent 仅作为无状态的认知辅助与交互加速层；任何涉及采购金额变更、状态流转、权限分配与合同生效的操作，必须无条件收敛至 Odoo 底层对象关系映射（ORM）引擎与状态机校验，由底层安全规则执行强制拦截。第二项纪律是奉行“配置优先于扩展、扩展优先于新建、确定性逻辑优先于大模型推理”的克制开发原则，通过精确识别 Odoo 原生能力边界，将定制开发工作量压缩至最小闭环。

针对当前阶段尚未探明的五项关键业务变量——组织规模与角色复杂度、采购审批节点深度、Odoo 现有部署状态、AI 与常规系统的职责切分、客户预算及签约主体要求——工程方案不应采取单一的静态假设，而应建立参数化的客户对齐诊断与工程分档矩阵。在进入正式商务报价前，实施团队可通过表 1-1 所示的收敛矩阵，将客户的业务现状直接映射为确定的技术方案分支与工期系数：

## 二、工作项 02：Odoo 版本选型与功能差距分析

在启动任何代码编写之前，明确“什么不需要开发”是控制工程成本的首要前提。围绕显微镜设备企业的三大核心业务领域（供应商与采购合同、人事与权限、会议与通知），首先需完成 Odoo 底座版本的技术选型，进而对原生模块进行深度的能力拆解与技术陷阱排查。

### 2.1 Odoo 社区版与企业版选型决策

### 2.2 原生采购模块的隐蔽工程陷阱与填补策略

通过对 Odoo 17 至 20 源码及标准采购模块（purchase）机制的深入剖析，虽然社区版与企业版均原生提供了“采购订单审批（Purchase Order Approval）”开关与“最低金额（Minimum Amount）”阈值配置，但其默认工程实现存在四项隐蔽的业务逻辑缺陷。若直接交付原生模块而不做针对性补丁，将在客户试点阶段引发严重的业务失控。

首要工程陷阱在于**审批待办的“静默挂起”缺陷**。在原生 Odoo 中，系统将采购订单含税总额（amount_total）与设定的最低阈值进行严格比对，当金额达到或超过阈值时，采购员点击确认订单会将状态推入“待审批（to approve）”。然而，原生系统在触发这一状态跃迁时，既不会向审批负责人自动发送电子邮件，也不会在系统中创建待办活动（mail.activity），仅在底部讨论区（Chatter）向关注者记录一条状态变更日志，并将单据置于待审批列表中。这与企业版 Studio 审批规则或独立 Approvals 应用会自动为每位审批人派发待办活动的机制截然不同。在原生社区版下，如果审批负责人不主动打开采购模块筛选“待审批”视图，该采购申请将无限期停滞。因此，定制扩展必须在状态跃迁至 to approve 时，通过重写确认方法钩子，自动为审批组负责人生成一条带截止时间的 mail.activity 强提醒。

第二项关键风险源于**管理员自建订单的“免审穿透”漏洞**。原生源码逻辑将采购模块权限划分为普通采购用户（Purchase User）与采购管理员（Purchase Administrator）两级。当单据进入待审批状态后，任何拥有采购管理员权限的用户均可点击批准按钮，且采购管理员对自己创建的采购订单默认豁免金额阈值检查，点击确认时将直接跳过待审批环节而生效。在初创型显微镜企业中，采购负责人往往既参与日常高价值零部件寻源建单，又持有审批权限；若不在权限配置上严格剥离建单人与审批人角色，或者不在代码层增加“制单人与审批人职责分离（Segregation of Duties）”校验，审批控制将彻底失效。

第三项机制缺陷体现在**询价单（RFQ）对外发送缺乏前置拦截以及确认后的篡改风险**。原生金额阈值检查仅挂载在“确认订单（Confirm Order）”动作上，这意味着普通采购员在询价阶段仍可针对任意高额订单向供应商发送询价邮件或导出报价单，仅在最终确认转为正式采购订单时才受系统拦截。此外，若未开启“锁定已确认订单（Lock Confirmed Orders）”设置，已获批生效的采购订单仍可能被事后静默修改单价或数量。因此，工程实施必须强制激活已确认订单自动锁定功能，并在视图层限制非授权状态下正式采购订单模板的打印与外发。

第四项功能差距在于**缺乏结构化审批审计字段与独立合同台账**。标准 purchase.order 模型并未内置专门的“审批人”或“审批时间”结构化数据库字段，审批动作仅作为普通文本日志保存在底部 Chatter 中，难以支持结构化检索与权责审计。同时，原生采购协议模块（purchase.requisition）主要存在于企业版或作为招标与一揽子协议（Procurement Tenders）使用，旨在从单一请购单派生多份询价单，无法直接满足国内企业围绕正式采购订单登记合同编号、跟踪质保期及归档盖章扫描件的合同台账需求。

## 三、工作项 01 & 03：核心业务建模与系统详细工程设计

基于差距分析结论，MVP 阶段的定制代码将严格封装在一个独立的自定义 Odoo 插件模块 microscope_office_mvp 中（依赖原生模块 base、mail、purchase、project、hr），坚决不直接修改 Odoo 核心源码目录，以确保未来系统升级与容器化迁移的纯净性。

### 3.1 显微镜零部件采购主流程与状态机设计

针对核心演示场景“采购一套显微镜设备零部件（如高数值孔径物镜、精密压电陶瓷聚焦台或科研级相机）”，系统通过确定性的有限状态机管理单据生命周期，并在状态转换边上植入强制守卫条件与副作用钩子，以修补原生 Odoo 的自审绕过与无通知挂起缺陷。

在需求提报与询价录入阶段（draft 至 sent 状态），采购专员在 Odoo 中创建询价单（RFQ），选择显微镜零部件供应商（partner_id），录入零部件明细、原厂料号、数量及供应商含税报价，并将供应商发来的报价单扫描件作为附件挂载于单据底部讨论区中。当询价信息核对无误后，流程进入提交确认与金额网关分流阶段。采购专员点击“确认订单（button_confirm）”按钮，系统拦截该动作并比对含税总额（amount_total）与公司设定的最低审批金额阈值。若订单总额低于阈值且操作者具备确认权限，单据直接跃迁至正式采购订单（purchase）并自动锁定为 done 状态，防止事后未经授权编辑已生效订单；若订单总额达到或超过阈值（在 MVP 演示期内可将阈值设为 0.01 元，以强制所有显微镜零部件采购均进入审批通道），单据状态立即跃迁至待审批（to approve）状态。在此状态跃迁瞬间，自定义扩展钩子自动检索归属于采购管理员组（purchase.group_purchase_manager）的审批负责人账号，调用 activity_schedule() 生成“采购订单待审批”系统活动，触发顶部状态栏提醒并写明申请摘要，彻底解决原生系统待审批单据无人知晓的痛点。

随后流程进入负责人审批与职责分离校验阶段（to approve 至 purchase/done 或 cancel 状态）。持有采购管理员权限的负责人打开待办单据，审阅零部件技术规格、比价记录与报价附件。当负责人点击“批准订单（button_approve\[span_170\](start_span)\[span_170\](end_span)\[span_194\](start_span)\[span_194\](end_span)）”时，自定义守卫逻辑首先校验当前审批人是否与制单人为同一账号（record.user_id != env.user），防止建单人越权自审；验证通过后，系统自动将当前用户与系统时间写入自定义的 approved_by_id 与 approved_date 字段，自动将待办活动标记为已完成，通过 mail.thread 向采购专员发送审批通过通知，并将单据推进至已确认且锁定状态。反之，若负责人点击“拒绝”，系统弹出必填拒绝原因向导，将原因记入审计消息流并将单据回退或取消。订单正式获批后，即进入采购合同登记与双向关联阶段，采购专员通过单据顶部的“关联合同”智能按钮创建或绑定 purchase.contract 记录，完成合同编号、签署日期、质保期限及盖章扫描件的归档闭环。

## 四、工作项 04：AI Agent 能力架构、工具边界与安全回退设计

在企业级 ERP 系统中引入大语言模型，最大的工程风险是“权限逃逸”与“幻觉写库”。若允许 AI Agent 使用一个共享的超级管理员账号直接连接数据库或调用 Odoo 接口，普通研发人员即可通过自然语言诱导让 Agent 查询公司核心光学器件的采购底价，甚至直接修改订单状态。因此，Agent 架构设计的核心在于构建强制继承当前登录用户权限上下文的“受控工具沙盒”。

### 4.1 身份透传与 Odoo RPC 权限继承机制

Odoo 外部接口（XML-RPC、JSON-RPC 以及 Odoo 19+ 引入的 JSON-2 API）在架构设计上直接暴露底层 ORM 方法，每一次外部 API 调用都必须提供认证凭据，并由 Odoo 内核自动按该凭据对应用户的访问权限（ir.model.access）、记录规则（ir.rule）和字段权限进行强制校验。基于这一原生安全机制，工程方案摒弃了高风险的“全局单一管理员 Bot 账号”模式，转而采用“按用户上下文动态鉴权（Per-User Context Impersonation）”架构。

在协议与适配器选型层面，针对 Odoo 18 底座，Agent 网关服务通过标准的 JSON-RPC 协议（向 /jsonrpc 或 /web/dataset/call_kw 发送 POST 请求）与 Odoo 通信，相比传统的 XML-RPC 协议，JSON-RPC 负载体积减少 40% 至 60% 且解析更为高效。同时，鉴于 Odoo 官方文档已将传统 XML-RPC 与 JSON-RPC 标记为逐步弃用，并计划在 Odoo 22 中移除而全面转向基于 Bearer Token 的 JSON-2 API，Agent 网关内部将 Odoo 连接器封装为独立的 OdooRPCClient 抽象接口层，确保未来升级至更高版本时仅需切换底层传输适配器，而无需改动上层 Agent 工具逻辑。

在用户级权限继承实现上，当员工在 Odoo Web 界面唤起 AI 助手面板时，前端请求携带当前员工的会话上下文（Session Cookie）或系统为该员工绑定的个人受限 API Key（自 Odoo 14 起支持 API Key 代替密码鉴权，且 Odoo 18+ 支持设置密钥过期时间以强化安全轮换）。Agent 网关在执行任何工具调用（Tool Call）时，均以该员工的真实 uid 与凭据向 Odoo 发起调用。凭借这一机制，当一名普通研发人员向 Agent 提问“帮我查一下上个月向供应商采购物镜的合同底价是多少”时，Agent 虽会触发合同查询工具并以该研发人员的 uid 向 Odoo 发起 search_read 请求，但 Odoo ORM 层的访问控制与记录规则会立即阻断该操作，并在返回的 HTTP 200 JSON 响应体中抛出 odoo.exceptions.AccessError 异常。Agent 网关捕获该异常结构体后，将其转化为标准安全提示：“当前账号无权访问采购合同及供应商报价数据”，从而在数据库访问层彻底杜绝越权泄密。

### 4.2 Agent 工具注册表与读写权限分级清单

MVP 阶段严格遵循“少而精”的工具设计原则，仅向大模型暴露 6 个高内聚、强类型校验的业务工具（4 个只读查询工具与 2 个草稿生成工具）。为规避 Odoo RPC 调用的常见性能与安全陷阱，所有工具在网关代码层均植入三项硬性防护规则：第一，统一使用 search_read 替代分离的 search 加 read 调用以减少网络往返，并强制显式声明 fields 白名单数组——因为 Odoo 的 read 与 search_read 若不指定 fields 参数，默认会返回该用户可读的全部字段（例如单个合作伙伴记录默认返回多达 121 个字段），不仅严重拖慢响应，还会瞬间撑爆大模型上下文窗口；第二，强制设定 limit 与 offset 分页参数（限制单次 limit \<= 20），因为 Odoo 原生 search 默认不分页，未加限制的查询会一次性加载全表匹配记录导致内存溢出，统计总数则统一调用轻量级的 search_count 方法；第三，在物理代码层彻底移除任何对应订单审批（button_approve）、订单确认（\[span_10\](start_span)\[span_10\](end_span)\[span_36\](start_span)\[span_36\](end_span)button_confirm）或权限修改的方法接口。具体工具规格如表 4-1 所示：

## 一、项目破局策略与不确定性收敛框架

针对初创期显微镜设备企业的数字化建设诉求，当前工程设计的核心矛盾在于客户需求尚处于高模糊度的意向阶段，而软件工程交付要求具备严密的边界定义、可量化的工作量估算以及无歧义的验收标准。显微镜设备行业涵盖光学部件、精密机械载物台、光电探测器及配套控制系统的组装与贸易，具有典型的多品种、小批量、高单价零部件采购特征，供应商询报价往来频繁，且零部件技术规格书与质保合同高度绑定。若在未明确业务流转细节与组织架构的前提下直接进入编码阶段，实施团队极易陷入无限期的需求蔓延与免费运维泥潭。

针对当前阶段尚未探明的五项关键业务变量，即组织规模与角色复杂度、采购审批节点深度、Odoo 现有部署状态、AI 与常规系统的职责切分、以及客户预算与签约主体要求，工程方案不应采取单一的静态假设，而应建立参数化的客户对齐诊断与工程分档矩阵。在进入正式商务报价前，实施团队可通过表 1-1 所示的收敛矩阵将客户的口头反馈直接映射为确定的技术方案分支与工期系数。

### 2.1 Odoo 社区版与企业版选型决策

\### 2.2 原生采购模块的四大隐蔽工程陷阱与填补策略

通过对 Odoo 17 至 20 源码及标准采购模块（purchase）机制的深入剖析可以发现，虽然社区版原生提供了“采购订单审批（Purchase Order Approval）”开关与“最低金额（Minimum Amount）”阈值配置，但其默认工程实现存在四项极其隐蔽的业务逻辑缺陷。若直接交付原生模块而不做针对性补丁，将在客户试点阶段引发严重的业务失控。

第一项缺陷是审批待办的“静默挂起”问题。在原生 Odoo 中，当采购订单含税总额（amount_total）达到或超过设定的最低阈值时，采购员点击确认订单会将状态推入“待审批（to approve）”。然而，原生系统此时不会向审批负责人发送任何邮件，也不会创建待办活动（mail.activity），仅在底部讨论区（Chatter）向关注者记录一条状态变更日志，并将单据在列表中标黄显示。如果审批负责人不主动打开采购列表筛选“待审批”视图，该采购单将无限期停滞，这与企业版 Studio 审批规则或 Approval\[span_162\](start_span)\[span_162\](end_span)\[span_164\](start_span)\[span_164\](end_span)s 应用会自动为审批人生成待办活动的机制截然不同。因此，定制扩展必须在状态跃迁至 to approve 时，通过重写 button_confirm 钩子自动为审批组负责人生成一条带截止时间的 mail.activity 强提醒。

第二项缺陷是管理员自建订单的“免审穿透”漏洞。原生源码逻辑规定，任何拥有“采购管理员（pur\[span_64\](start_span)\[span_64\](end_span)chase.group_purchase_manager）”权限组的用户，在确认自己创建的采购单时，系统会自动绕过金额阈值校验直接批准生效。在小微企业中，采购主管往往既负责日常寻源建单又持有较高权限；若不严格遵循制单人仅授予 Purchase User 权限、审批人不直接建单的配置规范，或者不在代码层增加“制单人与审批人职责分离（Segregation of Duties）”校验，审批流将形同虚设。

第三项缺陷在于询价单（RFQ）对外发送缺乏前置拦截。原生金额阈值校验仅挂载在“确认订单（button_confirm）”动作上，这意味着普通采购员在询价阶段即可针对任意高额订单点击发送邮件或打印报价单发给供应商，仅在最终转为正式采购订单时才被系统拦截。针对显微镜核心光学部件采购，工程设计需在视图层限制非授权状态下正式订单 PDF 模板的打印，严格区分“内部询价草稿”与“正式生效采购单”的单据抬头与操作权限。

第四项缺陷是缺乏结构化审批人字段与独立合同台账。标准 purchase.order 模型没有内置专门的“审批人（approved_by\[span_83\](start_span)\[span_83\](end_span)\[span_94\](start_span)\[span_94\](end_span)）”与“审批时间（approved_date）”结构化字段，审批痕迹仅散落在非结构化的底部消息流（Chatter）中，不利于直观检索与审计报表导出。与此同时，原生采购协议模块（purchase.requisition）实质上是面向企业版长期框架招标或一揽子协议（Procurement Tenders）设计的，且从采购申请（PR）到询价单（RFQ）的自动流转主要受限于企业版特性，无法直接满足国内企业“一单一合同或框架合同绑定多笔订单、登记合同扫描件、追踪质保期与付款节点”的轻量化合同管理诉求。

## 三、工作项 01 & 03：核心业务建模与系统详细工程设计

基于差距分析结论，MVP 阶段的定制代码将严格封装在一个独立的自定义 Odoo 插件模块 microscope_office_mvp 中，声明依赖原生模块 base、mail、purchase、project 与 hr。工程实施坚决不直接修改 Odoo 核心源码目录，以确保未来系统升级与容器化迁移的纯净性。

### 3.1 显微镜零部件采购主流程与状态机设计

针对核心演示场景“采购一套显微镜设备零部件（如高数值孔径物镜、精密压电陶瓷聚焦台或科研级 sCMOS 相机）”，系统通过确定性的有限状态机（Finite State Machine）管理单据生命周期。针对原生 Odoo 存在的“自审绕过”与“无通知挂起”两大缺陷，工程设计在状态转换边（Transition Edge）上植入了强制守卫条件（Guard Conditions）与副作用钩子（Side-effect Hooks），将完整业务流转划分为四个紧密衔接的阶段。

在第一阶段（需求提报与询价录入，draft 至 sent 状态）中，采购专员（或由研发人员提报经采购专员接手）在 Odoo 中创建询价单（RFQ），选择显微镜零部件供应商（partner_id），录入零部件明细、原厂料号、数量及供应商含税报价，并可将供应商发来的 PDF 报价单作为附件挂载于单据底部 Chatter 消息流中。

进入第二阶段（提交确认与金额网关分流，draft/sent 至 to approve 或 purchase 状态）后，采购专员点击“确认订单（button_confirm）”按钮，系统立即拦截该动作并依据含税总额（amount_total）执行双重校验。若订单总额严格低于系统设定的最低金额阈值且当前操作者具备确认权限，单据直接跃迁至正式采购订单（purchase）并自动锁定为 done 状态，通过启用原生“锁定已确认订单（Lock Confirmed Orders）”设置，防止任何人在订单发送给供应商后静默篡改价格或数量。反之，若订单总额达到或超过最低金额阈值（在 MVP 演示期间可将阈值设为 0.01 元，以强制所有显微镜零部件采购均需负责人把关），单据状态即刻跃迁至 to approve（待审批）。此时，自定义扩展钩子自动检索归属于 purchase.group_purchase_manager 权限组的审批负责人账号，调用 activity_schedule() 生成“采购订单待审批”系统活动，触发顶部状态栏提醒与邮件通知，从而彻底修补原生系统不发通知的缺陷。

在第三阶段（负责人审批与职责分离校验，to approve 至 purchase/done 或 cancel 状态）中，持有采购管理员权限的负责人打开单据，审阅零部件规格、历史比价记录与报价附件。当负责人点击“批准订单（button_approve）”时，自定义守卫逻辑首先校验制单人与审批人是否为同一账号（record.user_id != env.user，若初创公司规模极小、总经理既建单又审批，可通过系统配置参数动态开关此项校验）。校验通过后，系统自动将当前操作人 ID 与时间戳写入结构化字段 approved_by_id 与 approved_date，自动将该单据关联的待办活动标记为已完成，向制单采购员发送审批通过通知，并将单据推进至已确认/已锁定状态。若负责人点击“拒绝（button_reject）”，系统则弹出必填拒绝原因向导，将驳回理由持久化写入 mail.thread 审计流并将单据打回草稿或取消。

在第四阶段（采购合同登记与双向关联，purchase/done 关联 purchase.contract）中，订单获批生效后，采购专员点击单据顶部的智能按钮（Smart Button）“关联合同”，创建或绑定已有的 purchase.contract 台账记录，录入合同编号、签署日期、光学部件质保期限（如 24 个月）并上传双方盖章版合同 PDF 扫描件，从而实现从采购寻源、审批授权到合同归档的端到端完整闭环。

## 四、工作项 04：AI Agent 能力架构、工具边界与安全回退设计

在企业级 ERP 系统中引入大语言模型（LLM），最大的工程风险是“权限逃逸”与“幻觉写库”。若允许 AI Agent 使用一个共享的超级管理员账号直接连接数据库或调用 Odoo 接口，普通研发人员即可通过自然语言诱导（Prompt Injection）让 Agent 查询公司核心光学器件的采购底价，甚至直接修改订单状态。因此，Agent 架构设计的核心在于构建强制继承当前登录用户权限上下文的“受控工具沙盒（Controlled Tool Sandbox）”。

### 4.1 身份透传与 Odoo RPC 权限继承机制

Odoo 外部接口（XML-RPC、JSON-RPC 以及 Odoo 19+ 引入的 JSON-2 API）在架构设计上直接暴露底层 ORM 方法，每一次外部 API 调用都必须提供认证凭据，并由 Odoo 内核自动按该凭据对应用户的访问权限（ir.model.access）、记录规则（ir.rule）和字段权限进行强制校验。基于这一底层特性，本工程方案严禁使用全局单一高权限 Bot 账号模式，而是采用“按用户上下文动态鉴权（Per-User Context Impersonation）”架构。

在协议与适配器选型层面，针对 Odoo 18 底座，Agent 网关服务通过标准的 JSON-RPC 协议（向 /jsonrpc 或 /web/dataset/call_kw 端点发送 JSON 负载）与 Odoo 通信，相比传统的 XML-RPC 协议，其负载体积缩减 40% 至 60% 且解析更为高效。同时，鉴于 Odoo 官方已将传统 XML-RPC 与 JSON-RPC 标记为弃用并计划在 Odoo 22 移除，转而采用基于 Bearer Token 和命名参数的 JSON-2 API，Agent 网关内部将 Odoo 连接器封装为独立的 OdooRPCClient 抽象接口层，确保未来升级至 Odoo 19/20+ 时仅需切换底层传输适配器而无需改动任何 Agent 工具逻辑。

在用户级权限 100% 继承的实现路径上，当员工在 Odoo Web 界面唤起 AI 助手面板时，前端请求携带当前员工的会话上下文（Session Cookie）或系统为该员工动态绑定的个人受限 API Key（存储于安全凭据库，遵循 Odoo 18+ 规范配置 90 天定期轮换策略）。Agent 网关在执行任何工具调用（Tool Call）时，均以该员工的真实 uid 与凭据发起 execute_kw 调用。如此一来，底层 ORM 将自动阻断任何越权行为：例如当一名普通研发人员向 Agent 提问“帮我查一下上个月采购蔡司物镜的合同底价是多少”时，Agent 尝试以该研发人员的 uid 调用 search_read 访问 purchase.contract 模型，Odoo ORM 层的 ir.model.access 与 ir.rule 立即触发拦截，并在 HTTP 200 的 JSON-RPC 响应体 erro\[span_17\](start_span)\[span_17\](end_span)\[span_43\](start_span)\[span_43\](end_span)r.data.name 中返回 odoo.exceptions.AccessError 异常。Agent 网关捕获该异常后，将其转化为标准安全提示（“当前账号无权访问采购合同及供应商报价数据”），从而在数据库访问层彻底杜绝越权泄密。

### 4.2 Agent 工具注册表与读写权限分级清单

MVP 阶段严格遵循“少而精”的工具设计原则，仅向大模型暴露 6 个高内聚、强类型校验的业务工具（4 个只读查询工具与 2 个草稿生成工具），并在网关层植入针对 Odoo RPC 特性的三项硬性防护规则。首先，所有工具调用强制显式声明 fields 字段白名单数组，因为 Odoo 的 read 与 search_read 方法若不传入 fields 参数，默认会返回该用户可读的全部字段（例如 res.partner 默认返回多达 121 个字段），这不仅严重拖慢接口响应，更会瞬间撑爆大模型的上下文窗口并造成敏感信息泄露。其次，由于 Odoo 的 search 方法默认不分页，会一次性返回所有匹配记录，所有 Agent 查询工具在代码层强制设定分页上限 limit \<= 20，超出部分仅调用 search_count 返回统计总数，并且所有过滤域（Domain）严格采用嵌套列表语法（如 \[\['state', '=', 'to approve'\]\]）进行组装校验。最后，网关在物理层面隔离高危写操作，Agent 工具箱中不存在任何对应订单审批（button_approve）、订单确认（button_confirm）、金额修改或权限变更的接口映射。表 4-1 详细列出了 MVP 阶段的 Agent 工具注册表与安全边界。

### 4.3 会议纪要转待办工作流与模型异常降级机制

针对 MVP 验收标准中的“从模拟纪要生成待办，人工确认后保存”以及“模型接口失败不影响核心业务操作”，工程设计采用异步解耦与确定性回退（Circuit Breaker & Deterministic Fallback）模式。当用户在 meeting.minutes 表单中输入会议记录并点击“AI 智能提取待办”时，Odoo 后端将会议文本及参会人员列表（attendee_ids 的姓名与系统 ID 映射字典）发送至 Agent 网关。网关调用国内合规大模型 API，通过结构化输出约束（Structured Outputs / JSON Schema）强制模型输出包含会议结论摘要（summary）与待办事项数组（todos，含事项描述、建议责任人 ID、建议截止日及原文依据）的严格 JSON 格式。

解析成功的条目仅被写入当前会议记录的下属暂存明细表 meeting.minutes.line 中，将主单状态更新为 ai_extracted。用户在 Odoo 表单界面直接审阅可编辑的待办草稿列表，可随时修正大模型因同音字或语境歧义识别有误的责任人、调整截止日期或取消勾选无需立项的条目，最后点击原生确定性按钮 action_confirm_create_tasks。此时，纯 Python 确定性代码在单个数据库事务中遍历已勾选草稿行，批量创建 project.task 记录并向对应责任人派发 mail.activity 通知，全程不再依赖大模型推理。

在异常熔断与故障隔离方面，Odoo 向 Agent 网关发起的 HTTP 请求严格设置连接超时 3 秒、读取超时 15 秒。若外部大模型 API 出现公网抖动、配额耗尽或服务宕机，网关在超时瞬间立即捕获异常并向 Odoo 返回标准错误码，同时在 ai.agent.audit.log 中记录故障原因与重试状态。Odoo 界面捕获该状态后弹出非阻断式友好提示，引导用户直接在下方 meeting.minutes.line 表格中手动新增待办行并点击确认派发。由于所有外部大模型网络 I/O 调用均与核心 ERP 数据库事务完全解耦，即便 AI 服务完全不可用，采购建单、负责人审批、合同归档及手动任务分派等核心业务操作仍保持 100% 正常运转。

### 5.2 Odoo 原生 RPC 安全漏洞封堵与数据合规方案

根据对 Odoo 底层认证机制的深入调研，原生 Odoo 存在一项极易被忽视的架构级安全隐患：**默认情况下，每一个内部用户都是潜在的外部 API 用户**。只要外部人员获取了某位员工的登录邮箱与密码（或泄漏的 API Key），即可通过公网直接调用 /xmlrpc/2/common、/xmlrpc/2/object 或 /jsonrpc 接口读写数据库；更严重的是，原生 Odoo 对 XML-RPC 路径上的失败登录尝试既不记录标准审计日志，也没有内置暴力破解冷却限流机制。

为彻底封堵这一安全缺口，工程设计在基础设施层与应用层实施三重加固。第一重加固是在 Nginx 反向代理网关层直接封锁公网对 /xmlrpc/ 与 /jsonrpc 的非浏览器会话调用，将 agent-service 对 odoo-server 的 RPC 调用完全限制在 Docker 内部桥接网络（internal_net）中完成，使外部公网无法直接触达 RPC 认证端点。第二重加固是在 Odoo 用户模型（res.users）中引入账号级 API 访问白名单开关与“仅限 API Key 鉴权（API-Keys-Only）”策略，拒绝使用明文密码进行外部 RPC 认证，并在系统设置中配置全局紧急熔断开关（Global Kill Switch）——一旦监测到异常调用，管理员可一键切断所有外部 API 与 Agent 通道，而丝毫不影响员工通过浏览器正常登录使用 Odoo Web 界面。第三重加固聚焦于大模型 API 数据合规与商业机密保护：显微镜企业的供应商底价、核心光学零部件型号与客户合同属于核心商业机密，Agent 服务严禁连接未经备案的境外公网模型接口，统一采用国内合规企业级大模型 API（如阿里云百炼 Qwen 企业版或火山引擎 DeepSeek 企业专线，默认承诺不将企业 API 数据用于模型训练），并在 Prompt 组装层自动剥离供应商银行账号、税号等无关敏感字段。

### 5.3 自动化备份恢复与运维责任边界

在数据持久性与灾备机制设计上，部署环境内置自动化定时备份容器，遵循 3-2-1 备份原则，于每日凌晨 02:00 自动执行 pg_dump -Fc 导出 PostgreSQL 数据库一致性快照，同时完整打包 /var/lib/odoo/filestore 文件存储目录（确保所有上传的采购合同 PDF 与供应商报价单附件与数据库记录严格同步）。备份归档包经 AES-256 加密后自动上传至异地云端对象存储（如阿里云 OSS 或腾讯云 COS），本地磁盘保留最近 7 天快照、云端保留最近 30 天快照，并提供一键恢复脚本供验收测试验证。

在运维责任边界切分上，商务合同需明确界定试点验收期（及免费质保期内）实施方与客户方的权责边界。实施方负责保障 microscope_office_mvp 模块与 agent-service 代码缺陷修复（Bug Fix）、数据库自动备份脚本正常运行以及容器异常重启恢复。而云服务器资源续费、域名与 SSL 证书续期、第三方大模型厂商 API Token 充值及厂商侧服务中断、以及因客户管理员自行在 Odoo 后台开启“开发者模式（Debug Mode）”修改底层视图或删除数据库字段所引发的系统故障，均明确划归客户自担或按独立有偿运维协议计费处理，从而保护实施团队免受无边界免费运维的消耗。

## 七、从阶段 A 迈向阶段 B 的立项对齐行动清单

当前顶层架构、数据模型、权限矩阵与 Agent 安全边界已在工程逻辑上实现完全自洽，标志着项目圆满完成阶段 A（顶层设计）的既定目标。为顺利推进至阶段 B（客户对齐）与阶段 C（商业确认），避免在首次深度需求沟通会上被客户发散的设想带偏节奏，实施团队应携带本报告中的《功能差距矩阵》与《采购状态机沙盒》，围绕表 7-1 所列的 8 个结构化锚定问题引导客户做出明确决策。

| 序号   | 现场对齐核查问题（面向显微镜企业负责人）                                                                            | 客户预期回答选项                                                       | 对应的工程锁死动作                                                                    |
|--------|---------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------|---------------------------------------------------------------------------------------|
| **Q1** | 首期使用系统的员工总共有几人？分别负责什么岗位？是否存在“负责人自己下采购单”的情况？                                | 明确人数（如 8 人），确认采购员与审批人是否分离                        | 锁定 res.groups 账号分配表；若老板需自建自审，配置免审白名单开关                      |
| **Q2** | 采购一套显微镜零部件，从询价到下单，是否只需要“采购员提报 -\> 总经理（或主管）一级审批”即可？                       | A. 一级审批足够；B. 必须按金额分两级以上审批                           | 若选 A，直接采用原生审批+通知补丁（0 额外成本）；若选 B，触发《增项包 A》报价         |
| **Q3** | 询价阶段是否需要系统对比多家供应商报价？还是线下沟通好价格后，仅在系统录入最终选定供应商的报价并上传其它比价附件？  | 首期建议引导客户采用“主单录入 + 附件留存比价记录”                      | 锁死 RFQ 界面复杂度，避免首期开发复杂的在线供应商招投标门户                           |
| **Q4** | 采购合同是一笔订单签一份合同，还是与核心光学供应商签年度框架合同、分批下采购单？合同需要记录哪些核心要素？          | 明确关联关系（1:1 或 1:N），确认是否只需记录编号、金额、质保期与扫描件 | 锁定 purchase.contract 与 purchase.order 的外键关联方式及必填校验规则                 |
| **Q5** | 哪些采购信息（如具体供应商名称、零部件采购单价、合同扫描件）是普通研发或行政人员绝对不能看到的？                    | 确认数据保密边界（通常研发仅看型号与到货状态，不看底价）               | 锁定 ir.rule 行级过滤规则与价格字段的 groups="purchase.group_purchase_user" 属性      |
| **Q6** | 日常开会是谁负责记录纪要？大家平时用什么工具看任务通知（浏览器电脑端为主，还是必须发到微信/飞书）？                 | 引导首期在 Odoo Web 端内闭环验证会议提取与任务跟踪                     | 锁定 meeting.minutes 交互界面；将企微/飞书推送明确划入试点成功后的二期工程            |
| **Q7** | 公司目前是否有现成的云服务器、已备案域名，或者是否已经安装过某个版本的 Odoo？                                       | 确认是全新部署还是已有环境，确认国内云厂商倾向                         | 锁定 Docker Compose 部署清单；若已购 Odoo Online 则立刻预警需迁移至自托管 ECS         |
| **Q8** | 针对首期 3–4 周落地的 MVP 试点项目，公司的预算区间大概在什么范围？财务付款是否接受工作室/个人合同与分阶段验收付款？ | 探明真实资金预期与财务合规底线                                         | 匹配《表 6-1 商业报价模型》，在 48 小时内输出正式《MVP 实施范围说明书与分阶段报价单》 |
