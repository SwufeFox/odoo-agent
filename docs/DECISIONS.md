# 实现决策

## ADR-001：唯一测试基线 Odoo 20 Community

用户明确要求 Odoo 20。以官方 20.0 源码固定提交构建，不声明其他主版本兼容。PostgreSQL 17 用于本机和 Compose；部署凭据由本地初始化生成。

## ADR-002：单一 add-on

`microscope_office_mvp` 依赖 Contacts、Purchase、Project、HR、Mail。Odoo ORM 是唯一业务事实来源；无需独立 FastAPI 服务、第二份业务数据库或共享管理员 API Key。

## ADR-003：保密边界

普通员工不授予采购或合同模型访问权，因此不能通过采购表、订单行、供应商报价读取底价。采购/负责人使用原生采购权限；会议限主持人、参与者及负责人；公告限目标员工且仅发布后可见。按公司隔离记录。任务复用 `project.task`，增加会议任务访问约束以补足原生项目权限。

ASSUMPTION：员工首期不需要查看采购申请进度，因此不为其开放删减价格的采购视图。`purchase.order.user_id` 保持原生采购负责人语义。

## ADR-004：人工确认与幂等

报价、会议和通知先保存可编辑准备内容。会议只预填唯一匹配的参会人和明确日期，未知项留空；用户核对后一次采纳，可新增任务、更新已有任务或仅保留决定。任务截止日期允许留空。事务锁与业务关联保证重复采纳不重复创建，也不覆盖已采纳后的人工修改；输出中的人员和目标必须经当前用户权限及公司范围校验。

## ADR-005：本地演示边界

只监听 loopback，PostgreSQL 不发布容器端口。禁用外发邮件；演示账号密码与模型密钥仅保存到忽略目录。人工业务路径不依赖 AI。规则模式清楚标为本地规则示例；真实模型结果单独记录实际来源。

## ADR-006：统一模型客户端与可核对的准备内容

按用户指定接入 OpenAI 兼容端点与 `commandcode/deepseek/deepseek-v4.1-flash`。报价、会议及通知共用客户端，通过 `MOPS_AI_MODE` 显式选择规则或模型方式；当前配置和最近成功来源分开。模型只返回准备内容，Odoo 校验字段、原文依据及可访问的真实候选；金额由确定性代码计算。模型拒绝、超时或输出无效时保留原工作并显示错误，不静默改用规则结果。

## ADR-007：复用业务记录完成工作接续

报价准备写入原生 RFQ 草稿，会议接续原生 Project 任务，员工通知准备经负责人转为既有公告草稿。工作台只汇总当前用户可读且显式关联的记录，不复制业务状态或扩大权限。六个开发分工不对应运行时六模型调用；列表、导航、金额和权限仍由普通代码处理。

## 尚待客户确认

真实审批与自审政策、部门与跨公司边界、合同主体和关联基数、公告接收范围、模型授权与数据分类。售前环境不承诺生产 SLA、备份恢复或合规认证。
